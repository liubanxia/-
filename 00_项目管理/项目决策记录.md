## 决策001：采用完全离线运行架构

**状态：** 已确认  
**决策内容：**

医院正式运行环境不得依赖外网、云端模型或在线API。

**原因：**

1. 医院电脑可能无法访问外网。
2. 医疗数据不得上传到公共网络。
3. 离线架构更利于隐私保护和稳定运行。
4. 系统必须在网络中断时继续工作。

决策021：多CT Series必须由医生显式选择

状态： 已确认

原因：

同一检查中可能存在多个CT Series，例如不同重建层厚、不同算法、不同窗重建或定位像。
仅根据图像数量自动选择Series，可能导致错误进入非目标序列。

决策内容：

1. 当仅检测到1个CT Series时，允许直接进入阅片。
2. 当检测到2个及以上CT Series时，系统不得自动选择。
3. 必须向医生显示可识别的Series信息，例如：
   - SeriesDescription
   - SeriesNumber
   - 图像数量
   - 其他可安全获取的DICOM序列信息
4. 医生明确选择后，系统才允许加载该Series进入阅片。
5. 无法确认目标Series时，系统必须停止，不得猜测。
6. M8.0-E中的“自动选择图像数量最多Series”仅为开发阶段临时验证逻辑，不作为正式临床逻辑。

决策022：CT阅片前必须完成病例与Study身份一致性校验

状态： 已确认

原因：

同一目录或后续PACS工作流中可能出现不同患者、不同检查或身份字段缺失的DICOM。
若在身份不明确的情况下继续加载，存在混合病例、混合检查和错误阅片风险。

决策内容：

1. CT序列进入阅片前必须检查PatientID。
2. CT序列进入阅片前必须检查StudyInstanceUID。
3. CT序列进入阅片前必须检查SeriesInstanceUID。
4. 检测到多个PatientID时必须安全停止，禁止混合病例。
5. 检测到多个StudyInstanceUID时必须安全停止，禁止混合检查。
6. PatientID、StudyInstanceUID或SeriesInstanceUID缺失时必须安全停止。
7. 身份信息无法确认时不得自动猜测、自动选择或继续进入阅片。
8. 病例与Study身份校验通过后，才允许进入Series分组和医生显式选择流程。

验证结果：

M8.0-G已使用真实CT及构造测试数据验证：
- 多PatientID拦截成功；
- 多StudyInstanceUID拦截成功；
- 缺失PatientID拦截成功；
- 缺失StudyInstanceUID拦截成功；
- 缺失SeriesInstanceUID拦截成功；
- 正常单Study CT及多Series流程回归正常。

决策023：CT切片必须依据DICOM真实空间几何进行排序

状态： 已确认

原因：

CT阅片、病灶定位、层面记录和后续AI分析均依赖正确的切片空间顺序。
文件名、InstanceNumber、SliceLocation或单独使用ImagePositionPatient的Z坐标，都不能在所有CT扫描方向下可靠表示真实空间顺序。
对于倾斜扫描，必须结合ImageOrientationPatient与ImagePositionPatient计算切片在真实空间中的位置。

决策内容：

1. CT切片必须具有唯一且非空的SOPInstanceUID。
2. 检测到重复SOPInstanceUID时必须安全停止。
3. CT切片必须具有有效的ImagePositionPatient。
4. CT切片必须具有有效的ImageOrientationPatient。
5. ImageOrientationPatient的行、列方向向量必须有效且近似正交。
6. 同一Series内各切片图像方向必须保持一致；方向无法确认时安全停止。
7. 使用ImageOrientationPatient行、列方向向量叉乘得到切片法向量。
8. 将ImagePositionPatient投影到切片法向量，所得空间位置作为切片排序依据。
9. 检测到两个不同SOPInstanceUID对应实质重复空间位置时必须安全停止。
10. 不再使用SliceLocation、InstanceNumber、文件名顺序或默认0.0作为CT空间排序的自动回退依据。
11. 无法可靠确定空间顺序时，不猜测、不继续进入阅片。
12. SliceThickness允许在同一Series中变化。
13. 相邻切片空间间距不要求恒定；仅凭非等距不得判定Series异常或阻止加载。

验证结果：

M8.0-H已使用真实倾斜CT及构造测试数据验证：
- 28张真实CT依据IOP与IPP空间投影正常排序和加载；
- 多Series医生显式选择流程回归正常；
- 重复SOPInstanceUID拦截成功；
- 缺失SOPInstanceUID拦截成功；
- 缺失ImagePositionPatient拦截成功；
- 缺失ImageOrientationPatient拦截成功；
- Series内图像方向不一致拦截成功；
- SOP唯一但空间位置重复拦截成功；
- 真实数据存在4mm与7mm不同层厚及非恒定层间距，系统未进行错误拦截。

决策024：CT/DX像素处理必须统一入口，CT HU标定禁止猜测

状态： 已确认

原因：

CT阅片中的HU值、窗宽窗位显示及后续AI定量分析依赖可靠的原始像素数据与DICOM标定信息。
如果RescaleSlope或RescaleIntercept缺失时自动使用1和0，会产生未经证实的HU值，形成医学数据猜测。
同时，像素处理逻辑若分别存在于界面层和DICOM模块中，会造成不同入口具有不同安全行为。

决策内容：

1. CT与DX像素处理统一收口到dicom/pixel.py。
2. UI层只负责调用统一像素处理接口和显示，不自行维护另一套HU计算逻辑。
3. CT必须能够正常读取并解码PixelData。
4. 当前V1仅接受二维单帧灰阶像素矩阵。
5. CT必须具有有效的Rows与Columns，且必须与实际像素矩阵尺寸一致。
6. 当前V1 CT要求SamplesPerPixel为1。
7. CT PhotometricInterpretation仅接受MONOCHROME1或MONOCHROME2。
8. BitsAllocated、BitsStored、HighBit和PixelRepresentation必须存在且满足基础合法性检查。
9. RescaleSlope与RescaleIntercept必须存在、可转换为有限数值。
10. RescaleSlope或RescaleIntercept缺失或异常时，禁止使用默认1/0推测HU值，必须安全停止。
11. 医生选定CT Series并完成空间排序后，在正式进入阅片前必须预检查全部切片的像素数据与HU标定。
12. 任意一层预检查失败时，整个目标Series不得进入正式阅片状态。
13. 阅片过程中仍保留运行时切片读取与显示异常保护，作为第二道安全防线。
14. 运行时翻层失败时必须恢复上一层索引和CT状态，禁止出现界面层号与实际显示影像错位。
15. DX（DR）统一通过normalize_dx()处理，避免UI层与像素模块产生不同显示逻辑。
16. 无法确认真实像素数据或HU标定时，不猜测、不继续用于医学分析。

验证结果：

M8.0-I已完成以下验证：
- 28张真实CT全部像素检查及HU转换通过；
- 正常CT主界面加载、窗宽窗位及循环翻层正常；
- 缺失RescaleSlope拦截成功；
- 缺失RescaleIntercept拦截成功；
- 第14层缺失RescaleSlope时，在进入阅片前完成拦截；
- 正常CT全Series预检查无误拦；
- Series进入阅片后模拟第2张切片文件失效，运行时拦截成功且程序未崩溃；
- DX synthetic_DX.dcm主界面显示回归正常。

决策025：CT目录扫描不得静默忽略疑似或损坏DICOM文件

状态： 已确认

原因：

CT序列完整性直接关系到医学阅片安全。
如果目录扫描阶段遇到异常DICOM后直接continue，系统可能在医生不知情的情况下少加载切片，形成“静默漏层”。
普通非DICOM文件可以存在于目录中，但任何已经具有可信DICOM身份、CT身份或标准DICM前导的异常文件，都不得被无提示跳过。

决策内容：

1. 禁止在CT目录扫描阶段使用通用 `except Exception: continue` 静默忽略异常文件。
2. 普通txt等明确不具备可信DICOM结构的文件允许忽略。
3. 带标准DICM前导的文件视为明确DICOM候选，读取失败时必须安全停止。
4. 对无DICM前导文件允许使用force读取进行身份鉴别，但不得因此直接判定其已受当前V1支持。
5. 无DICM前导但具有可信CT DICOM身份结构时，当前V1必须明确提示暂不支持并安全停止，不得静默忽略。
6. CT Image Storage的标准SOP Class UID为：
   1.2.840.10008.5.1.4.1.1.2
7. 当前V1仅接受标准CT Image Storage进入普通CT阅片流程。
8. 当SOPClassUID表明文件属于CT Image Storage，而Modality缺失或异常时，必须安全停止。
9. 禁止因Modality缺失而把CT切片当作非CT文件跳过。
10. 标准DICOM读取成功后仍必须检查最基本的SOP身份结构。
11. SOP Class与SOP Instance身份均无法确认时，按可能损坏DICOM处理并安全停止。
12. SOP身份可从Dataset或File Meta中确认，避免因存储位置差异造成误拦。
13. 无法确认某异常文件是否影响目标CT Series完整性时，优先停止，不猜测、不静默少层。
14. 多Series仍必须保持医生显式选择流程，不因本决策改变。

验证结果：

M8.0-J已完成以下验证：
- 正常28张CT与普通文本文件共存时，正常加载28张；
- 无DICM前导但具有可信CT DICOM结构时安全停止；
- 第14张CT删除Modality后，旧逻辑曾静默加载27张；修复后安全停止；
- 构造带DICM但内容损坏的标准DICOM，pydicom虽可宽松解析但缺失基本SOP身份；修复后安全停止；
- 正常28张真实CT回归通过；
- 多Series医生显式选择流程回归正常。

决策026：Project Phoenix采用医生主动激活的双视觉AI架构

状态： 已确认

原因：

普通CT整体阅片需要兼顾多类异常，但骨折尤其是细小、隐匿及多发骨折容易漏诊，且逐层、逐骨检查耗时较大。
单一视觉模型同时承担全局异常筛查和高敏感骨折搜索，容易造成任务目标冲突。
因此将常规综合阅片与骨折漏诊防护拆分为两条独立视觉通路。

决策内容：

1. Project Phoenix视觉AI采用双视觉架构。

2. 视觉A定义为：
   常规综合阅片AI。
   负责普通CT的全局异常候选搜索、定位及后续综合阅片任务。

3. 视觉B定义为：
   骨折漏诊防护AI。
   专门针对骨骼连续性及骨折候选进行高敏感搜索，作为医生骨折漏诊防护的第二视觉通路。

决策027：视觉AI采用ONNX Runtime CPU-only推理底座与显式模型配置

状态： 已确认

原因：

Project Phoenix要求完全离线、Windows环境可部署、CPU优先、轻量化，并且视觉A与视觉B后续需要能够独立替换模型。
因此推理运行层必须与具体医学模型解耦，并避免依赖GPU、云端服务或系统级Python环境。

决策内容：

1. Project Phoenix V1视觉AI优先采用ONNX Runtime作为本地推理底座。

2. 当前正式推理Provider固定为：
   CPUExecutionProvider。

3. 不允许Phoenix自动选择Azure、GPU或其他Provider作为替代路径。

4. ONNX模型采用延迟加载：
   - 创建主窗口时不加载模型；
   - 创建视觉A/视觉B包装对象时不加载模型；
   - 只有医生主动启动AI并真正进入推理时才建立ONNX Session。

5. 医生停止双视觉AI后：
   - 推理权限立即关闭；
   - 已加载Session可以暂时保留在内存中；
   - Session存在不得绕过医生授权继续推理。

6. ONNX模型必须支持显式unload，用于模型切换、程序退出或主动释放内存。

7. 视觉A与视觉B使用独立模型、独立Session、独立预处理及独立输出解析，互不影响。

8. 模型路径集中配置于Phoenix配置层。
   当前模型目录固定为：
   - 视觉A：04_AI模型/视觉A_综合阅片
   - 视觉B：04_AI模型/视觉B_骨折防护

9. 具体模型文件名必须显式配置。
   禁止程序自动扫描目录、自动猜测模型、自动选择替代模型。

10. 当前V1模型路径解析只允许.onnx模型，并禁止通过模型文件名跳出指定模型目录。

11. AI CT像素预处理必须复用现有dicom/pixel.py：
    - 使用ct_to_hu()完成经过安全校验的HU转换；
    - 使用apply_window()执行窗宽窗位处理；
    - 禁止AI层另建第二套HU计算逻辑。

12. Phoenix统一CT AI基础输入当前定义为：
    已验证CT DICOM → HU → 指定窗 → float32 → 0.0~1.0。

13. 当前建立2.5D三层基础输入：
    [前一层, 当前层, 后一层] → (3, H, W)。

14. 2.5D预处理层不负责寻找相邻切片，不根据InstanceNumber猜测层面，也不假定层间距恒定。
    切片顺序必须来自已经通过DICOM空间几何排序的上层逻辑。

15. resize、通道排列、模型均值/标准差、输入尺寸、窗参数及后处理规则等模型特定参数，必须在真实医学模型确定后依据其训练规范显式配置，禁止提前猜测。

16. M9.0-B当前只建立真实模型接入基础设施，不宣称已经具备真实医学诊断能力。

决策028：视觉B骨折候选采用切片身份绑定与安全点击定位机制

状态： 已确认

原因：

视觉B产生的骨折候选最终需要由医生在真实CT序列中复核。
如果候选只记录显示序号，或在病例、Study、Series切换后继续保留旧候选，
可能造成候选指向错误切片甚至错误病例。

因此候选结果必须与已经通过Phoenix安全门控及空间排序的当前CT上下文绑定，
医生点击候选时必须再次进行切片身份核对，不能仅依赖界面列表位置直接跳转。

决策内容：

1. 视觉B输出定义为“骨折候选”，不等同于骨折诊断结论。

2. 单个骨折候选至少保存：
   - 当前排序后的slice_index；
   - 对应DICOM的SOPInstanceUID；
   - 原始confidence；
   - 候选区域类型；
   - 候选区域数据；
   - 来源“视觉B”；
   - 任务类型“骨折候选”。

3. slice_index只表示Phoenix当前已经通过安全门控并完成DICOM空间排序后的序列位置。
   禁止根据InstanceNumber重新猜测候选切片位置。

4. SOPInstanceUID作为候选切片身份核对依据。
   医生点击候选准备跳层时，程序必须重新读取目标切片并核对实际SOPInstanceUID。

5. 如果候选保存的SOPInstanceUID与目标切片实际SOPInstanceUID不一致：
   - 禁止跳转；
   - 保持当前CT状态；
   - 在状态栏显示安全停止信息。

6. 候选点击跳层统一复用Phoenix现有CT切片显示入口。
   不为视觉B另建第二套CT读取、HU转换或窗宽窗位显示逻辑。

7. 候选跳层时应保持医生当前CT窗宽窗位状态。
   视觉B不得因为候选定位擅自修改医生正在使用的显示状态。

8. 视觉B候选统一保存于独立FractureCandidateStore中。
   UI只展示候选，不直接把界面文字作为医学结果数据源。

9. 右侧“视觉B骨折候选”列表用于医生主动选择和复核候选。
   当前M9.0-C实现的最小显示信息为：
   Slice位置与Confidence。

10. 医生点击右侧候选后执行：
    候选选择 → 取得对应FractureCandidate → SOP身份核对 → CT安全跳层。

11. 新病例、Study、Series或单DICOM上下文变化时：
    - 必须清空FractureCandidateStore；
    - 必须同步清空右侧视觉B候选列表；
    - 禁止任何上一影像上下文的骨折候选继续显示或继续使用。

12. 视觉A结果不得自动删除、覆盖或否定视觉B骨折候选。
    视觉B候选必须由医生独立复核。

13. 当前M9.0-C只建立候选数据结构、候选存储、列表展示及安全CT定位链路。
    候选框/掩膜叠加、医生确认/驳回、跨层候选合并及真实骨折模型输出解析留待后续阶段实现。

决策029：视觉B候选叠加显示与医生复核状态分离机制

状态： 已确认

原因：

视觉B骨折候选需要在真实CT影像上提供直观定位，同时医生需要能够对候选进行确认或否定。

候选框属于辅助显示信息，不应修改原始DICOM、HU数据或基础影像像素。
医生复核意见也不应覆盖或改写模型原始候选，否则会造成模型输出与医生判断混淆，不利于后续审计、学习及错误分析。

因此视觉B采用“原始候选、显示叠加、医生复核状态”三层分离设计。

决策内容：

1. FractureCandidate继续保存视觉B原始模型候选，不保存医生最终复核意见。

2. 候选bbox只作为显示层叠加，不得修改：
   - 原始DICOM；
   - HU数组；
   - Phoenix保存的原始current_pixmap。

3. 候选叠加必须基于current_pixmap副本绘制，再统一缩放显示。

4. 当前M9.0-D只实现bbox叠加。
   mask候选当前安全忽略，待后续明确mask格式后再实现。

5. bbox当前采用原始影像像素坐标：
   (x1, y1, x2, y2)。

6. bbox必须具有正面积，并限制在真实影像边界内。
   非法、非有限或无法解析的bbox不得破坏正常阅片显示。

7. 视觉B候选只有同时满足以下条件时才允许在当前影像上显示：
   - 候选属于当前slice_index；
   - 当前DICOM的SOPInstanceUID与候选完全一致；
   - 候选region_type为当前支持的bbox。

8. 医生点击候选后必须先完成原有CT安全跳层及SOPInstanceUID身份核对。
   只有定位成功后，才允许将其设为当前活动复核候选并显示bbox。

9. 候选定位失败时：
   - 禁止激活新候选；
   - 禁止显示新bbox；
   - 医生复核按钮保持禁用；
   - 旧活动候选叠加必须取消，避免误导。

10. 医生滚动离开候选所属切片时，bbox自动隐藏。
    返回该候选切片且身份仍一致时，bbox自动恢复。

11. 窗口缩放、CT调窗及重新渲染时，候选叠加必须通过统一显示入口重新生成，不得把标注永久画入原始影像。

12. 医生复核状态独立保存，不修改FractureCandidate原始对象。

13. 当前医生复核状态定义为：
    - pending：待复核；
    - accepted：医生确认保留该候选；
    - rejected：医生否定该候选。

14. accepted仅表示医生确认“保留该视觉B候选”，不等同于已经确诊骨折。

15. 医生复核状态当前以FractureCandidateStore中的候选索引绑定。

16. 当前活动复核候选同时保存：
    - active_fracture_candidate；
    - active_fracture_candidate_index。

17. 医生提交确认或否定前，程序必须再次验证：
    - 当前活动候选存在；
    - 候选索引合法；
    - Store中该索引对象与当前活动候选为同一对象。

18. 活动候选身份失效时：
    - 禁止写入医生复核状态；
    - 清空活动候选及索引；
    - 禁用复核按钮；
    - 移除候选叠加；
    - 状态栏显示安全停止信息。

19. 右侧视觉B候选列表当前显示：
    - Slice位置；
    - Confidence；
    - 医生复核状态。

20. 当前医生操作按钮为：
    - 确认候选；
    - 否定候选。

21. 未成功选择并定位合法候选前，两个复核按钮必须保持禁用。

22. 新病例、Study、Series或单DICOM上下文变化时，必须同步清空：
    - FractureCandidateStore；
    - 右侧候选列表；
    - active_fracture_candidate；
    - active_fracture_candidate_index；
    - 医生复核状态；
    - 旧bbox显示；
    - 复核按钮启用状态。

23. 即使新影像随后加载失败，上一个影像上下文中的旧bbox也不得继续残留显示。

24. 当前M9.0-D只完成候选bbox显示及医生确认/否定交互。
    尚未实现：
    - mask叠加；
    - 跨层候选合并；
    - 医生修改原因记录；
    - 学习流程联动；
    - 真实骨折模型推理结果接入。

25. 当前阶段仍不宣称Project Phoenix已经具备真实骨折诊断能力。

决策030：视觉B模型输出解析与候选原子注入机制

状态： 已确认

原因：

不同视觉B骨折模型的ONNX输出格式可能不同，但Phoenix内部的候选结构、DICOM身份绑定、医生复核及UI链路必须保持稳定。

如果具体模型直接生成UI数据，或由模型自行猜测DICOM切片身份，会造成模型实现与临床安全链路耦合，并增加错误切片绑定、候选覆盖及历史有效结果丢失的风险。

因此视觉B采用“模型专用decoder → Phoenix统一输出解析器 → FractureCandidate → 原子候选注入”的分层机制。

决策内容：

1. OnnxVisualA现有output_parser接口保持不变：
   output_parser(raw_outputs)。

2. OnnxVisualB的output_parser扩展为：
   output_parser(raw_outputs, series_context)。

3. 视觉B输出解析器必须获得当前已经通过Phoenix安全门控的series_context，不能只依据模型原始输出猜测DICOM身份。

4. 新建VisualBOutputParser作为Phoenix视觉B统一输出解析层。

5. VisualBOutputParser本身不得猜测任何具体ONNX模型输出格式。

6. 每个真实视觉B模型必须显式提供自己的decoder。
   decoder只负责：
   原始模型输出 → Phoenix标准候选草稿。

7. 当前标准候选草稿至少必须包含：
   - slice_index；
   - confidence；
   - region_type；
   - region。

8. decoder不得负责生成或猜测SOPInstanceUID。

9. VisualBOutputParser根据标准候选草稿中的slice_index，从当前series_files读取真实目标DICOM。

10. 目标切片的SOPInstanceUID必须从真实DICOM读取，并由Phoenix绑定到FractureCandidate。

11. slice_index必须为非负整数，并且必须位于当前CT Series范围内。

12. 当前VisualBOutputParser标准输出固定为：
    tuple[FractureCandidate, ...]。

13. 候选草稿缺字段、类型非法、slice_index越界或目标DICOM缺失SOPInstanceUID时，本轮解析必须失败。

14. 包含多个候选时，只要其中任一候选非法，本轮解析不得返回部分候选结果。

15. FractureCandidateStore新增replace_all()原子替换接口。

16. replace_all()必须先验证整个新候选批次。
    任一候选非法时，原Store保持完全不变。

17. 合法空候选批次允许替换当前Store为空，表示本轮视觉B明确完成推理但没有产生候选。

18. MainWindow建立_replace_visual_b_candidates()作为视觉B候选统一注入入口。

19. 新候选批次必须先成功完成Store原子替换，之后才允许清理上一轮：
    - active_fracture_candidate；
    - active_fracture_candidate_index；
    - 医生复核状态；
    - bbox叠加；
    - 复核按钮状态；
    - 右侧候选列表。

20. 新批次非法时，旧Store、旧候选列表、旧医生复核状态及旧bbox必须全部保持不变。

21. MainWindow建立_apply_visual_b_inference_result()作为双视觉调度结果进入视觉B候选链的安全入口。

22. 只有同时满足以下条件时，视觉B新结果才允许覆盖当前有效候选：
    - 视觉B通路error为None；
    - result为标准tuple；
    - tuple内全部对象均为FractureCandidate；
    - Store原子替换成功。

23. 视觉B推理失败时，不得清空或覆盖医生当前已经看到的有效候选。

24. 视觉B输出解析失败时，不得清空或覆盖当前有效候选。

25. 未经过VisualBOutputParser转换的原始ONNX输出不得直接进入FractureCandidateStore。

26. 当前MockVisualB返回普通字典，不属于标准FractureCandidate tuple，因此不得覆盖现有候选。

27. 合法空tuple表示视觉B本轮明确成功且无候选，此时允许清空上一轮候选。

28. 双视觉调度器继续保持视觉A与视觉B故障隔离，不因本决策改变其既有success、partial_failure及failed语义。

29. 视觉B标准候选进入Store后继续复用M9.0-C/M9.0-D已经建立的：
    - SOP安全点击定位；
    - bbox显示；
    - 医生确认/否定；
    - 上下文清空机制。

30. 当前M9.0-E只完成真实模型输出接入基础设施及Mock端到端验证。
    尚未确定真实骨折模型的：
    - ONNX输出张量格式；
    - 正式decoder；
    - 阈值；
    - 后处理；
    - 模型权重。

31. 当前阶段仍不宣称Project Phoenix已经具备真实骨折诊断能力。

决策031：视觉B真实模型配置契约与decoder安全边界

状态： 已确认

原因：

不同真实骨折模型可能具有完全不同的ONNX输入名、输出名、decoder、置信度阈值及空间结果类型。

Phoenix不得根据文件名、张量数量或常见模型格式自动猜测模型接口，否则真实模型更换后可能产生错误输入、错误decoder或错误候选绑定。

因此在M9.0-F建立视觉B真实模型显式配置契约。

决策内容：

1. 新建VisualBModelContract，作为视觉B真实模型接入的唯一显式模型契约。

2. 每个视觉B真实模型必须明确声明：
   - model_id；
   - input_builder_id；
   - decoder_id；
   - expected_input_names；
   - expected_output_names；
   - confidence_threshold；
   - allowed_region_types。

3. Phoenix不得自动猜测：
   - ONNX输入名；
   - ONNX输出名；
   - input_builder；
   - decoder；
   - 置信度阈值。

4. 当前allowed_region_types仅允许：
   - bbox；
   - mask。

5. confidence_threshold必须是0～1范围内的有限数值。

6. expected_input_names和expected_output_names必须：
   - 非空；
   - 不含空名称；
   - 不含重复名称。

7. input_builder生成的input_feed必须在ONNX模型加载前与expected_input_names进行精确校验。

8. input_builder输出名称错误时：
   - 禁止读取ONNX metadata；
   - 禁止建立无效推理流程；
   - 禁止执行模型infer；
   - 本轮安全失败。

9. OnnxVisualB创建对象时仍不得自动加载模型。

10. 第一次真实infer时才允许建立ONNX Session并读取模型metadata。

11. 第一次infer必须校验真实ONNX：
    - 输入名称；
    - 输出名称；
    与VisualBModelContract完全一致。

12. 当前阶段不自动猜测ONNX shape和dtype。

13. 模型契约成功验证后，同一Session连续推理不重复执行metadata契约验证。

14. OnnxVisualB执行unload()后：
    - ONNX Session释放；
    - 契约验证状态必须重置；
    - 下一次加载必须重新验证模型契约。

15. VisualBOutputParser必须绑定与OnnxVisualB相同语义的VisualBModelContract。

16. decoder仍然只负责：
    原始ONNX输出 → Phoenix标准候选草稿。

17. VisualBOutputParser负责模型级候选安全门控。

18. decoder输出候选低于confidence_threshold时允许安全过滤。

19. 低置信度候选必须在读取目标DICOM前完成过滤，避免无意义磁盘读取。

20. decoder输出的region_type不属于当前模型allowed_region_types时必须显式失败，不允许静默转换。

21. confidence非法、非有限或超出0～1范围时必须显式失败。

22. 本决策不得改变：
    - CPUExecutionProvider only；
    - 延迟加载；
    - 医生主动启动；
    - 原始DICOM只读；
    - FractureCandidate安全身份绑定；
    - Store原子替换机制。

23. M9.0-F当前仍属于真实模型接入基础设施阶段。

24. 当前仍未确定最终骨折模型权重和正式decoder，不宣称Phoenix已经具备真实骨折诊断能力。


决策032：多轻量专科视觉模型与高速模型路由架构

状态： 已确认

原因：

Project Phoenix的目标不是堆叠尽可能多的AI模型。

医院日常阅片真正需要的是：
- 快速；
- 稳定；
- 低CPU；
- 不影响PACS；
- 模型职责明确；
- 可解释；
- 可按需替换。

如果多个大型模型同时运行，会造成CPU、内存及磁盘占用增加，并可能导致PACS翻层和鼠标操作卡顿。

因此Phoenix采用“少量高价值专科模型 + 高速路由器”的架构。

决策内容：

1. 模型数量不是Phoenix的性能指标。

2. 模型选择优先级为：
   专科明确 > 稳定 > 速度 > 可维护 > 模型数量。

3. 专科模型优先按照“器官级/临床任务级”划分，不无限拆成每一种疾病一个独立模型。

4. Phoenix中枢采用：
   超轻量视觉路由器
   + 确定性状态机
   + 模型注册表。

5. 小型本地LLM不承担常规逐帧部位识别。

6. 小型LLM只在以下情况按需唤醒：
   - 路由结果存在歧义；
   - PACS界面状态异常；
   - 医生输入自然语言复杂指令；
   - 多任务工作流需要规划。

7. 普通病例优先由轻量视觉路由器直接识别：
   - Modality；
   - 解剖部位；
   - 当前层面；
   - 当前窗位/序列；
   - 当前任务状态。

8. 路由结果进入模型注册表后，只启动当前需要的专科模型。

9. 正常情况下同时活动的专科模型原则上控制在1～2个。

10. 无关模型必须保持未加载或休眠状态。

   - BiomedParse；

   MedSAM → LiteMedSAM。

    → 按PACS常用窗位和显示方式渲染
    → 生成2D/2.5D屏幕风格训练帧
    → 将3D标签映射到对应层面
    → 训练Phoenix轻量学生模型
    → ONNX/量化
    → 医院CPU按需运行。

13. Phoenix学生模型必须学习医生实际在PACS显示器中可见的视觉域，而不能假定正式运行时能够直接访问教师模型所依赖的完整3D原始数据。

    - 不同医院；
    - 不同PACS；
    - 不同显示分辨率；
    - 不同窗位显示；
    - 不同扫描设备；
    的泛化性能。

15. 正式采用任何外部教师模型前必须单独核查：

    - 是否允许衍生/蒸馏；

决策036：视觉B候选前置校验与契约一致性安全原则

状态： 已确认

原因：

M9.0-F第二轮安全测试发现，若置信度过滤早于候选结构校验，decoder产生的非法候选可能被低置信度静默吞掉；同时，OnnxVisualB与output_parser若允许绑定不同模型契约，会产生阈值及输出解释漂移。

另外，ONNX input_feed为字典，输入名称必须一致，但不得错误依赖Python字典键插入顺序。

因此进一步固定视觉B真实模型接入的安全顺序和数据结构不变量。

决策内容：

1. decoder输出的每个候选必须先完成结构合法性校验，再执行confidence阈值过滤。

2. 低置信度只允许过滤“结构合法但分数低”的候选，不得掩盖decoder结构错误。

3. 以下错误必须在读取目标DICOM前显式失败：
   - slice_index类型非法；
   - slice_index小于0；
   - slice_index超出当前Series范围；
   - region为空；
   - confidence非法、非有限或超出0～1；
   - region_type不符合当前模型契约；
   - bbox结构非法。

4. bbox统一采用：
   (x1, y1, x2, y2)

5. bbox必须满足：
   - 恰好4个坐标；
   - 坐标必须为可转换的有限数值；
   - bool不得作为bbox坐标；
   - x2 > x1；
   - y2 > y1。

6. bbox是否超出当前影像显示范围，不在候选结构层根据猜测裁剪；继续由UI依据真实显示尺寸安全裁剪。

7. VisualBOutputParser负责第一层bbox前置校验，尽可能在DICOM读取前终止非法候选。

8. FractureCandidate自身负责第二层数据结构不变量保护，防止未来其他模块绕过parser直接创建非法候选。

9. FractureCandidate中的合法bbox统一规范化为4个float。

10. OnnxVisualB配置output_parser时，output_parser必须显式绑定VisualBModelContract。

11. output_parser绑定的VisualBModelContract必须与OnnxVisualB使用的模型契约语义完全一致。

12. 模型契约内容一致即可，不强制两个Python对象具有相同对象身份。

13. output_parser=None仍允许用于明确的原始输出/调试通路。

14. VisualB input_feed的输入名称必须与expected_input_names集合完全一致：
    - 不允许缺少；
    - 不允许增加；
    - 不依赖Python字典键顺序。

15. ONNX output metadata仍保持有序名称严格校验，因为raw output的顺序可能直接影响decoder解释。

16. 当前阶段仍不自动猜测ONNX tensor shape、dtype、输入预处理方式或decoder。

17. 本决策不得改变以下长期原则：
    - CPUExecutionProvider only；
    - ONNX Session延迟加载；
    - 视觉B必须由医生人工点击后启动；
    - 未点击时不得后台自动推理；
    - 原始DICOM永久只读；
    - 候选必须绑定真实SOPInstanceUID；
    - Phoenix当前仍不宣称已经具备真实骨折诊断能力。

18. 本决策属于M9.0-F真实模型接入基础设施安全加固。


决策037：视觉B组件注册表与真实模型装配层

状态： 已确认

原因：

VisualBModelContract已经明确声明：

- model_id；
- input_builder_id；
- decoder_id；
- ONNX输入输出名称；
- confidence_threshold；
- allowed_region_types。

但如果input_builder_id和decoder_id仅作为字符串存在，而没有显式映射机制，Phoenix仍无法根据模型契约找到真实实现。

同时，如果真实模型的组件解析、模型路径解析、parser创建和OnnxVisualB创建全部直接写入UI层，将导致main_window.py承担模型配置、模型装配和界面职责，破坏模块化边界。

因此建立独立的视觉B组件注册表与真实模型装配层。

决策内容：

1. 新增VisualBComponentRegistry。

2. VisualBComponentRegistry当前只负责显式映射：

   input_builder_id
   → input_builder callable

   decoder_id
   → decoder callable。

3. 注册表禁止：
   - 自动搜索组件；
   - 根据名称相似度猜测组件；
   - 未注册ID自动回退；
   - 重复ID静默覆盖。

4. input_builder_id和decoder_id必须：
   - 为非空字符串；
   - 唯一注册；
   - 对应真实可调用对象。

5. 未注册input_builder_id或decoder_id时必须显式失败。

6. resolve_contract_components只接受正式VisualBModelContract。

7. 注册表当前不负责：
   - 模型文件路径；
   - ONNX Session加载；
   - 医学推理；
   - 专科路由；
   - UI控制。

8. 新增VisualBModelAssembler，作为视觉B真实模型装配层。

9. VisualBModelAssembler固定装配流程：

   VisualBModelContract
   → VisualBComponentRegistry解析组件
   → 显式模型路径解析
   → VisualBOutputParser
   → OnnxVisualB。

10. 装配器必须复用现有model_path_resolver，不允许重复建立模型文件搜索逻辑。

11. 组件解析必须早于模型路径访问。

12. 如果契约引用未注册组件：
    - 立即失败；
    - 不访问模型文件；
    - 不创建ONNX adapter。

13. 如果模型路径解析失败：
    - 立即失败；
    - 不继续创建OnnxVisualB；
    - 不执行任何推理。

14. VisualBModelAssembler只负责对象装配，不负责执行infer。

15. 装配阶段不得主动加载ONNX Session。

16. OnnxVisualB仍保持延迟加载：
    第一次经过合法医生门控后的真实infer时才允许建立ONNX Session。

17. 真实decoder继续由VisualBOutputParser调用，不允许OnnxVisualB自行猜测输出格式。

18. UI层不应长期承担：
    - model_id解析；
    - input_builder选择；
    - decoder选择；
    - parser构造；
    - ONNX模型装配。

19. 后续main_window.py应只接收已经装配好的视觉模型对象或由更高层运行配置提供视觉实例，避免UI与模型实现强耦合。

20. 本决策当前只完成视觉B基础设施，不代表真实骨折模型已经选定。

21. 当前仍未确定最终：
    - 骨折模型权重；
    - 正式input_builder；
    - 正式decoder；
    - 正式阈值；
    - 真实临床验证方案。

22. 本决策不得改变以下长期原则：
    - 医生主动点击后才能启动视觉AI；
    - 未点击时不得后台推理；
    - CPUExecutionProvider only；
    - 原始DICOM永久只读；
    - 模型接口不得自动猜测；
    - Phoenix当前不宣称已具备真实骨折诊断能力。
