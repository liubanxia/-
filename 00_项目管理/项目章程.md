1. 项目基本信息

项目中文名称：离线AI-PACS智能辅助阅片系统
项目英文代号：Project Phoenix
当前阶段：V1.0 工程开发阶段
项目性质：长期持续迭代的离线医学影像辅助软件工程
文档建立日期：2026年8月6日

────────

2. 项目使命

Project Phoenix 的使命是建立一套以医生为最终决策者、完全离线运行、可解释、可审计、能够积累经验并持续改进的医学影像智能辅助阅片系统。

系统不替代医生，不独立作出临床诊断，不自动签署报告。

系统的主要职责是：

1. 辅助医生浏览和分析当前病例。
2. 提供可核查的影像征象与报告草稿。
3. 根据医学规则和本地知识库检查报告问题。
4. 分析医生修改内容及修改原因。
5. 将经过确认和脱敏的错误病例转化为学习经验。
6. 帮助医生快速复习相似错误和相关医学知识。

────────

3. V1.0支持范围

V1.0仅支持：

1. 普通CT平扫。
2. 常规DR影像。

V1.0暂不支持：

1. 增强CT。
2. CTA。
3. MRI。
4. 超声。
5. PET/CT。
6. 病理图像。
7. 自动临床决策。
8. 自动签署或发送报告。

新增检查类型必须经过独立设计、验证和版本审批，不能直接混入V1.0。

────────

4. 最高设计原则

4.1 完全离线

医院正式运行环境不得依赖外网、云端模型或在线API。

医院电脑负责运行，SSD负责承载程序、模型、配置、规则、知识库和运行环境。

手机下载的软件、模型和资料必须经过检查后，再导入开发SSD。

4.2 医生主导

医生始终是最终决策者。

AI只能提供：

• 候选征象；
• 分析建议；
• 鉴别诊断；
• 报告草稿；
• 风险提示；
• 学习材料。

医生负责：

• 审核；
• 修改；
• 确认；
• 签署；
• 发送。

4.3 单病例原则

系统同一时间只能处理一个当前病例。

病例身份无法确认、病例发生切换、界面状态异常或当前病例信息不一致时，系统必须立即停止操作。

4.4 最小控制权限

AI只能执行经过批准的鼠标和键盘操作。

AI不得：

• 自动签署报告；
• 自动审核报告；
• 自动发送报告；
• 自动删除病例；
• 自动删除临床报告；
• 自动切换患者；
• 绕过医生确认；
• 修改医院系统安全设置。

4.5 可解释与可审计

每一项重要结论应尽可能关联：

• 影像征象；
• 所在层面；
• 解剖位置；
• 使用的医学规则；
• 参考知识来源；
• 模型版本；
• 医生修改记录。

系统不得只输出无法解释的最终结论。

4.6 CPU优先与轻量化

V1.0优先适配普通医院Windows电脑，采用CPU可运行的轻量模型和按需加载机制。

不得因为追求模型规模而导致PACS明显卡顿、医生操作受阻或系统无法在普通硬件运行。

4.7 模块化与长期维护

系统采用模块化架构。

核心能力包括：

• AI中央调度；
• 状态管理；
• PACS视觉观察；
• OCR；
• CT工作流；
• DR工作流；
• 多模型调度；
• 医学规则引擎；
• 报告生成；
• 本地知识库；
• 反思学习引擎；
• 经验库；
• 证据中心；
• 日志与恢复机制。

新增模块不得破坏现有模块的独立性和安全边界。

────────

5. 固定医学分析流程

所有影像分析默认遵循以下流程：

解剖定位
→ 病变识别
→ 技术前提确认
→ 客观征象描述
→ 性质判断
→ 鉴别诊断
→ 规范化报告

不得跳过技术前提直接作出诊断。

CT判读必须先确认窗宽窗位。

平扫CT不得描述强化、增强程度或增强方式。

不得编造：

• 病灶大小；
• CT值；
• 强化表现；
• 未显示的征象；
• 未提供的临床资料。

骨骼病变按以下顺序检查：

骨皮质
→ 骨松质或骨髓腔
→ 骨膜
→ 周围软组织

相邻器官区域的大型病变，必须通过连续层面确认器官连续性和病灶来源后再定性。

────────

6. 医学学习与纠错原则

医生修改AI报告后，系统可以分析：

1. 修改了什么。
2. 为什么修改。
3. AI属于漏诊、误判、定位错误、描述错误还是报告表达错误。
4. 哪一条规则或知识没有正确应用。
5. 是否存在相似历史错误。
6. 应当形成什么学习文档。

系统可以生成候选经验和候选规则，但不得未经医生确认自动升级为正式医学规则。

PDF书籍、指南和医院规范采用本地知识检索方式使用，不得在无人审核情况下自动修改模型权重。

────────

7. 截图与证据管理原则

AI完成报告草稿后，可以询问医生是否标注病灶。

只有医生明确选择“是”，系统才允许：

• 定位病变；
• 截取关键层面；
• 添加标注；
• 保存临时证据。

如果AI判断正确且医生未修改相关内容，临时截图原则上删除。

如果医生修改了相关结论，截图经脱敏后可进入学习中心和证据中心。

长期保存的截图不得包含：

• 患者真实姓名；
• 身份证号；
• 住院号；
• 检查号；
• 电话；
• 地址；
• 其他可直接识别患者的信息。

────────

8. 数据与隐私原则

Project Phoenix不得建立包含患者真实姓名的长期患者数据库。

临时处理当前病例所需的患者信息，只能在当前任务范围内短暂使用。

病例切换、任务结束或程序退出后，应按照数据生命周期规则清理临时身份信息。

所有进入经验库、测试库、证据中心和开发数据集的资料必须完成脱敏。

────────

9. SSD与运行环境原则

开发环境采用：

手机联网下载
→ 开发SSD保存
→ Windows电脑离线开发和测试

正式医院部署时，应采用独立生产SSD。

开发SSD可以存放：

• 开发工具；
• 源代码；
• 公开数据；
• 已脱敏数据；
• 测试模型；
• 项目文档。

生产SSD不得带到网吧，不得存放来源不明的软件，不得用于公开或未脱敏数据测试。

原则上一个医院使用一套独立生产SSD和独立配置。

────────

10. 开发流程

所有重要功能必须依次经过：

需求确认
→ 设计
→ 编码
→ 测试
→ 医学审核
→ 安全审核
→ 验收
→ 版本提交

未完成测试和验收的模块，不得进入正式医院运行环境。

每次重大修改必须：

1. 更新相关文档。
2. 更新开发日记。
3. 更新项目决策记录。
4. 完成Git提交。
5. 保留可回退版本。

────────

11. 项目禁止事项

禁止：

1. 在真实病例上直接测试未经验证的自动化操作。
2. 将患者真实信息带入网吧或公共电脑。
3. 让AI自动签署、审核或发送报告。
4. 在平扫CT中编造增强表现。
5. 编造未测量的数据。
6. 未确认病例身份时继续工作。
7. 未经医生确认自动生成正式医学规则。
8. 在正式生产SSD中保存开发实验文件。
9. 未经测试直接替换正式模型。
10. 为追求速度而绕过安全检查和医学审核。

────────

12. 项目完成标准

Project Phoenix V1.0只有同时满足以下条件，才可以进入试运行：

1. 能在目标Windows电脑完全离线启动。
2. 普通CT平扫和常规DR流程可以稳定运行。
3. 单病例状态控制可靠。
4. 医生能够随时接管和停止系统。
5. 不存在自动签署、发送、删除等越权行为。
6. 所有模型和规则均有明确版本。
7. 所有重要操作均有日志。
8. 医学输出经过系统性验证。
9. 隐私和脱敏机制通过测试。
10. 能够回滚到稳定版本。
11. 医生拥有最终审核和决定权。

────────

13. 项目最高结论

Project Phoenix 是医生的辅助工具，不是医生的替代者。

系统的价值不在于自动给出一个结论，而在于：

• 提高阅片完整性；
• 减少遗漏；
• 提供可核查证据；
• 帮助医生发现错误；
• 积累经过确认的经验；
• 形成可持续改进的离线医学知识体系。

任何功能设计都不得违背医生主导、安全优先、隐私保护、可解释和完全离线这五项最高原则。
